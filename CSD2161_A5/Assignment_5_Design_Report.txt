1. Design Introduction
================================================================================

Overview
----------------------------------------------
The system implements an online stock trading platform using a single TCP
channel for all client-server communication. Multiple clients connect
simultaneously to a central server to buy and sell stocks from a shared
market. All state is server-authoritative: the server validates every
trade, updates portfolios, adjusts market prices, and persists data to
disk.

The client features a graphical user interface built with Dear ImGui
(DirectX 11 backend), replacing the traditional console interface.

Matching Model: Market-maker quotes with bid/ask spread.
  - Ask price: the price clients pay when BUYING.
  - Bid price: the price clients receive when SELLING.
  - Buying pushes both bid and ask prices UP by $1 per trade.
  - Selling pushes both bid and ask prices DOWN by $1 per trade (min $1).

This spread ensures the market always profits from the difference between
bid and ask, simulating a real-world market-maker model.


1.1 TCP Binary Protocol
----------------------------------------------
All messages use a custom binary protocol over TCP with network byte order
(big-endian) for all multi-byte integers. Each message begins with a
1-byte Command ID identifying the message type, followed by command-
specific payload fields.

Variable-length fields (username, error text, history text) are length-
prefixed with a 4-byte uint32 so the receiver knows exactly how many
bytes to read. Fixed-length stock symbols use an 8-byte zero-padded
buffer.

Partial-read handling: Both server and client implement recvAll() and
sendExact() functions that loop until exactly N bytes have been received
or sent, ensuring complete message delivery even when the OS splits TCP
segments across multiple recv()/send() calls.

----------------------------------------------

Server Architecture:
  - The main thread runs an accept() loop, pushing each new client socket
    into a TaskQueue (producer-consumer thread pool with 10 worker threads
    and a bounded queue of 20 slots).
  - Each client is handled by one worker thread that reads the login
    command, then enters a command dispatch loop (buy/sell/market/
    portfolio/history/quit).
  - Shared state is protected by three mutexes:
      UsersMutex   - guards the user portfolio database (Database map)
      MarketMutex  - guards the stock market data (StocksDataBase map)
      g_clientsMutex - guards the connected client list (for broadcast)
  - After each buy or sell, the server broadcasts updated market data
    (RSP_MARKETUPDATE) to ALL connected clients.
  - On client disconnect, user and market data are saved to text files.

Client Architecture:
  - Built with Dear ImGui (immediate-mode GUI) and DirectX 11 rendering.
  - The main thread runs the Win32 message pump and ImGui render loop,
    reading shared state to draw the UI and sending commands on user input.
  - A dedicated receiver thread reads all server responses asynchronously,
    parses the binary protocol, and updates shared state (mutex-protected).
  - In Debug mode, the client uses Console subsystem (shows a console
    window alongside the GUI for debug output). In Release mode, it uses
    Windows subsystem (GUI only, no console).
  - UI Layout:
      Login dialog   : server IP, port, username entry
      Top bar        : shows logged-in username, cash balance, disconnect
      Market panel   : live table of stocks with Bid/Ask prices
      Activity log   : color-coded log of trades, errors, notifications
      Trading panel  : portfolio view, buy/sell forms, trade history


1.4 Transaction Sequences
----------------------------------------------

User Login
----------
Step  Client                   Direction  Server
1     REQ_LOGIN (NameLen,       ->
      Username)
2                               <-         RSP_LOGIN (Balance)
                                           (New users get $10,000)
3                               <-         RSP_MARKET (all stocks)

Buy Stock
---------
Step  Client                   Direction  Server
1     REQ_BUY (Symbol, Qty)    ->
2                                          Validates: stock exists,
                                           market has shares, user
                                           has enough cash
3                               <-         RSP_BUY (Symbol, Qty,
                                           UnitPrice, NewCash)
4                               <-         RSP_MARKETUPDATE
                                           (broadcast to ALL clients)
*     On validation failure:   <-         RSP_ERROR (error message)

Sell Stock
----------
Step  Client                   Direction  Server
1     REQ_SELL (Symbol, Qty)   ->
2                                          Validates: stock exists,
                                           user owns enough shares
3                               <-         RSP_SELL (Symbol, Qty,
                                           UnitPrice, NewCash)
4                               <-         RSP_MARKETUPDATE
                                           (broadcast to ALL clients)
*     On validation failure:   <-         RSP_ERROR (error message)

View Portfolio
--------------
Step  Client                   Direction  Server
1     REQ_PORTFOLIO            ->
2                               <-         RSP_PORTFOLIO (Cash,
                                           StockCount, [holdings...])

View Trade History
------------------
Step  Client                   Direction  Server
1     REQ_HISTORY              ->
2                               <-         RSP_HISTORY (MsgLen, Text)

Market Refresh
--------------
Step  Client                   Direction  Server
1     REQ_MARKET               ->
2                               <-         RSP_MARKET (all stocks)

Client Disconnect
-----------------
Step  Client                   Direction  Server
1     REQ_QUIT                 ->
2                                          Saves Database + Market
3                                          Removes client from list
4                                          Closes socket

Unexpected Disconnect (client crash / network failure)
------------------------------------------------------
Step  Client                   Direction  Server
1     Process killed                       recv() returns 0 or
                                           SOCKET_ERROR
2                                          Saves Database + Market
3                                          Removes client from list
4                                          Closes socket
5                                          Worker thread returns to
                                           pool (TaskQueue)


1.5 Price Movement Model
----------------------------------------------
The market uses a fixed-tick price movement model:

  - When a client BUYS stock:
      Trade executes at the current Ask price
      Both Ask and Bid prices increase by $1
      Market quantity decreases by trade quantity

  - When a client SELLS stock:
      Trade executes at the current Bid price
      Both Ask and Bid prices decrease by $1 (minimum $1)
      Market quantity increases by trade quantity

Example:
  Initial state: AAPL Bid=$146 Ask=$154 Qty=999
  Client buys 5 AAPL:
    Cost = 5 x $154 = $770
    New state: AAPL Bid=$147 Ask=$155 Qty=994
  Client sells 3 AAPL:
    Revenue = 3 x $147 = $441
    New state: AAPL Bid=$146 Ask=$154 Qty=997

The spread (Ask - Bid) remains constant. This model ensures price
discovery through supply and demand while maintaining simplicity.


1.6 Concurrency and Thread Safety
----------------------------------------------
Server:
  - TaskQueue implements a producer-consumer pattern with 10 worker
    threads and a bounded queue of 20 slots. The main thread produces
    (accepted sockets), workers consume and handle clients.
  - Lock ordering: MarketMutex is always acquired before UsersMutex
    in BuyStock() and SellStock() to prevent deadlock.
  - BroadcastMarket() acquires g_clientsMutex then MarketMutex to
    iterate over all clients and send updated market data.
  - SaveDatabase() and SaveMarket() are called on each client disconnect
    to ensure persistence even on unexpected shutdown.

Client:
  - A single mutex (g_stateMutex) protects all shared state between
    the main render thread and the receiver thread.
  - The receiver thread updates g_market, g_portfolio, g_cash, etc.
    under the lock.
  - The main thread reads these under the same lock when rendering.


1.7 Data Persistence
----------------------------------------------
Three text files store all server state:

  Users.txt   : One line per user.
                Format: Username Cash [StockName Qty Cost ...]
                Loaded at server startup, saved on each client disconnect.

  Stocks.txt  : One line per stock.
                Format: StockName Quantity BidPrice AskPrice
                Loaded at server startup, saved on each client disconnect.

  Trades.txt  : Append-only audit log. Each trade is timestamped.
                Format: YYYY-MM-DD HH:MM:SS Username ACTION Symbol
                        Qty @ Price (total: Total)

Default stocks: AAPL, GOOG, MSFT, AMZN, TSLA
New users start with $10,000 cash.

2.1 Testing Methodology
----------------------------------------------
Testing was performed locally (loopback 127.0.0.1) and across a switched
LAN with multiple client instances. All tests verify server-authoritative
state, correct price movement, multi-client broadcast, and data persistence.

2.2 Test Case Results
----------------------------------------------

Test 1: Client Login (New User)
  - Start Server, enter port 8888
  - Start Client, enter IP 127.0.0.1, port 8888, username "testuser"
  - Click "Connect & Login"
  - Expected: Login successful, balance $10,000 displayed
  - Result: PASS - Activity log shows "Login successful! Balance: $10000"
            Market data table populates automatically

Test 2: Client Login (Existing User)
  - Disconnect and reconnect with same username
  - Expected: Previous balance and portfolio restored
  - Result: PASS - Balance reflects prior trades, portfolio intact

Test 3: Buy Stock
  - Log in, enter symbol "AAPL", quantity 5 in Buy section, click "Buy"
  - Expected: Balance decreases by 5 x AskPrice, portfolio shows 5 AAPL
  - Result: PASS - Activity log shows BUY confirmation with price and
            new balance. Portfolio section updates.

Test 4: Buy Stock - Insufficient Funds
  - Attempt to buy more stock than cash allows
  - Expected: RSP_ERROR with "Not enough cash" message
  - Result: PASS - Activity log shows error in red

Test 5: Buy Stock - Insufficient Market Quantity
  - Attempt to buy more shares than market has available
  - Expected: RSP_ERROR with "Not enough shares available" message
  - Result: PASS - Error displayed correctly

Test 6: Buy Stock - Invalid Symbol
  - Enter a non-existent stock symbol and attempt to buy
  - Expected: RSP_ERROR with "Stock does not exist" message
  - Result: PASS

Test 7: Sell Stock
  - After buying AAPL, enter symbol "AAPL", quantity 2, click "Sell"
  - Expected: Balance increases by 2 x BidPrice, portfolio quantity
              decreases
  - Result: PASS - Activity log shows SELL confirmation

Test 8: Sell Stock - Insufficient Holdings
  - Attempt to sell more shares than owned
  - Expected: RSP_ERROR with "Not enough shares" message
  - Result: PASS

Test 9: Price Movement After Buy
  - Note AAPL Bid/Ask prices, buy 1 share, check prices
  - Expected: Both Bid and Ask increase by $1
  - Result: PASS - Market table reflects updated prices

Test 10: Price Movement After Sell
  - Note prices, sell 1 share, check prices
  - Expected: Both Bid and Ask decrease by $1
  - Result: PASS

Test 11: Market Broadcast to Multiple Clients
  - Connect Client A and Client B with different usernames
  - Client A buys a stock
  - Expected: Both Client A and Client B see updated market prices
  - Result: PASS - Client B receives RSP_MARKETUPDATE automatically

Test 12: View Portfolio
  - After several trades, check Portfolio section
  - Expected: Shows current cash and all stock holdings with quantities
  - Result: PASS

Test 13: View Trade History
  - Click "Load History" in Trade History section
  - Expected: All trades displayed with timestamps
  - Result: PASS - Full audit trail shown

Test 14: Data Persistence
  - Perform trades, disconnect client, stop server
  - Restart server, reconnect with same username
  - Expected: Balance, portfolio, and market prices preserved
  - Result: PASS - All data restored from Users.txt and Stocks.txt

Test 15: Multiple Concurrent Clients
  - Connect 3 clients simultaneously
  - Each client performs buy/sell operations
  - Expected: All trades execute correctly, market updates broadcast
              to all, no data corruption
  - Result: PASS - Server handles concurrent access with mutex protection

Test 16: Client Unexpected Disconnect
  - Close client window (Alt+F4) without sending REQ_QUIT
  - Expected: Server detects disconnect, saves data, cleans up client
  - Result: PASS - Server continues accepting new clients, data saved

Test 17: Market Refresh
  - Click "Refresh" button in Market panel
  - Expected: Market data re-fetched from server
  - Result: PASS
